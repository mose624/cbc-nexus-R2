Learning outcomes

After studying this chapter, learners should be able to explain the core concepts, analyse a realistic engineering problem, select and justify an appropriate method, communicate a design clearly, identify risks, and verify the resulting work against explicit criteria.

Study method: Read each topic, reproduce the diagrams from memory, complete the practical activity, answer the revision questions before checking guidance, and maintain a glossary of unfamiliar technical terms.

1. Database systems in software products

Database systems in software products is a core engineering concern because software systems must satisfy stakeholder needs while remaining understandable, testable and operable. Begin by stating the problem, the system boundary and the assumptions that shape the solution. Identify the people and services that interact with the system, the information they exchange, and the consequences of incorrect or delayed behaviour. A sound engineering decision is not simply a fashionable technology choice: it is a reasoned response to constraints, evidence and quality objectives.

In practice, document the decision before implementation. Record the alternatives considered, the advantages and limitations of each, and the reason the selected approach fits the context. Translate the decision into observable behaviour, interface contracts and acceptance criteria. Keep responsibilities cohesive, minimize unnecessary coupling, and define how errors, exceptional conditions and changes will be handled. Review the design with another developer and use a small experiment or prototype where uncertainty is high.

For a worked example, imagine a university learning portal serving students, lecturers and administrators. Trace one user task from the interface through the application logic to persistent data and operational monitoring. Identify validation points, permissions, expected responses and recovery behaviour. Then consider how the same design behaves when a user submits incomplete information, a dependency becomes unavailable, or demand rises sharply. This scenario turns abstract terminology into engineering decisions that can be inspected and tested.

Engineering check: Can another team member explain the purpose, inputs, outputs, dependencies, failure behaviour and verification method without relying on undocumented assumptions? If not, improve the specification and supporting evidence.

Practical laboratory / applied project

Work in a small team to design a modest feature for a campus learning portal. Produce a one-page problem statement, stakeholder list, system context diagram, concise requirements, a design sketch, a risk register and a test plan. Implement a small demonstrator or prototype where appropriate. Use version control, record meaningful commits, request peer review and keep evidence of decisions.

Submission evidence: problem statement; assumptions; diagram; decision log; prototype or pseudocode; test cases and results; short reflection. Your assessor should be able to trace each major requirement to a design decision and a verification activity.

Assessment rubric (100 marks): problem analysis 15; technical accuracy 20; design quality 20; implementation or prototype 15; testing and evidence 15; communication and reflection 10; collaboration and version-control practice 5.

Further study and academic integrity

Use current university textbooks, peer-reviewed research, official technical standards and primary product documentation to deepen this introductory framework. Check publication dates and version numbers because engineering tools and recommended practices evolve. Cite sources in the style required by your institution. Do not present generated text, code or diagrams as experimental evidence; independently verify every claim, calculation and implementation.
