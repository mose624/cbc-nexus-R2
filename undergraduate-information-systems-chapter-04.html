Purpose of systems design

Systems design translates approved requirements into a coherent description of how people, processes, data, software, infrastructure and controls will work together. Analysis establishes the problem and required outcomes; design specifies the solution structure and its behaviour. It is not merely screen drawing or database creation. It is a set of models, decisions and specifications that guide implementation, testing, deployment and maintenance.

A sound design balances usability, security, performance, availability, cost, accessibility and maintainability. Stakeholders may have conflicting priorities, so trade-offs and assumptions must be explicit. A design should be evaluated against measurable requirements and the real context of use. A technically elegant product that fails to support the work is unsuccessful, just as a convenient interface that exposes confidential information is unsuccessful.

Design principles and modularity

Separation of concerns assigns distinct responsibilities to different parts of a system. High cohesion means that the elements within a module contribute to a focused purpose; low coupling means modules depend minimally on other modules' internal details. Abstraction exposes essential behaviour while hiding unnecessary complexity, and encapsulation protects internal state behind defined interfaces. These principles improve comprehension, testing and changeability.

A module should have a clear contract: its purpose, inputs, outputs, errors, permissions and dependencies. Excessive fragmentation can be as harmful as a single tangled component. Designers should choose boundaries around stable business capabilities and avoid creating modules solely to make diagrams look sophisticated. Reuse is valuable when it reduces duplication without forcing unrelated requirements into one generic component.

Quality attributes and non-functional requirements

Quality attributes describe how well a system performs its functions. Performance concerns response time and throughput; availability concerns readiness for use; reliability concerns consistent operation; scalability concerns growth; security concerns protection against misuse; usability concerns effectiveness and satisfaction; accessibility concerns use by people with varied abilities; and maintainability concerns safe modification.

Broad words such as fast, secure and user-friendly must become testable scenarios. Specify the user or system stimulus, operating conditions, expected response and measurable threshold. For example, define a response-time percentile under a stated concurrent workload, a recovery-time objective after a named failure, or a keyboard-only completion test for a critical task. Targets should be agreed with business owners and tested under representative conditions.

System architecture and viewpoints

Architecture describes the major components of a solution, their responsibilities, interfaces, dependencies and deployment environment. It includes application structure, data ownership, integration, security boundaries and operational responsibilities. It is not simply a picture of servers. An architecture should explain how the system meets important quality attributes and how components cooperate to deliver business capabilities.

Different stakeholders require different views. A business view maps capabilities and value streams; an application view identifies services and interactions; a data view explains entities and flows; a technology view describes platforms and networks; a security view identifies identities and trust boundaries; and a deployment view maps software to runtime nodes. Views must be consistent and scoped to a question so that a single diagram is not mistaken for the whole design.

Architectural styles and patterns

A layered architecture separates presentation, application, domain and data-access responsibilities. Client-server architecture places user-facing clients in communication with shared services. A modular monolith packages capabilities in one deployable application while retaining internal boundaries. Service-oriented architecture and microservices divide capabilities into services with explicit contracts and independent deployment possibilities.

Microservices can support independent scaling and team autonomy, but introduce network failures, distributed data, monitoring, security and operational complexity. Event-driven architecture uses published events to decouple producers and consumers, but must handle duplicate delivery, ordering and eventual consistency. No style is universally superior. Choose a pattern because its properties solve a real requirement, not because it is fashionable.

Web and client-server architecture

A web application commonly includes a browser or mobile client, an application server, data stores and external services. The client presents information and gathers input; the server authenticates requests, validates data, applies business rules and returns a response. HTTPS protects communication in transit. Supporting services may provide identity, payment, email, file storage, search or analytics.

Client-side validation improves interaction but is not a security boundary because users can alter browser code or send requests directly. Important rules must be enforced on the trusted server. Public browser code must not contain privileged credentials or unrestricted database access. Design also considers caching, session handling, cross-origin policies, rate limits, browser compatibility, responsive layouts and graceful failure.

Data architecture and database selection

Data architecture defines the information an organisation needs, its authoritative source, representation, ownership, movement, quality and lifecycle. A model should express business concepts rather than reproduce the layout of an old spreadsheet. Entities, attributes, identifiers, relationships, constraints and reference data must have consistent meanings across applications.

Relational databases suit structured records and transactions; document stores support flexible document-shaped records; key-value stores support rapid lookups; graph databases represent connected relationships; and analytical warehouses support reporting. Selection depends on consistency, query patterns, scale, skills, governance and cost. Persistence design must address concurrency, backup, retention, deletion, archival, audit and recovery, not only storage capacity.

Conceptual, logical and physical data modelling

A conceptual model identifies major business entities and relationships without selecting a database technology. In a university system, entities may include Applicant, Application, Programme, Offer, Student, Course and Enrolment. It helps stakeholders agree on scope and meaning before technical detail dominates the discussion.

A logical model adds attributes, identifiers, cardinalities and integrity rules. It answers whether an applicant can submit several applications and whether a student can enrol in many course offerings. A physical model translates the logical design into tables, columns, data types, indexes and database constraints. Physical optimisation must preserve logical meaning; denormalisation may improve read speed but creates duplicated values that require controlled updates.

Relational design and normalisation

First normal form removes repeating groups and requires fields to hold atomic values appropriate to their domain. Storing several telephone numbers in one comma-separated field makes validation and querying difficult. Second normal form removes partial dependencies on part of a composite candidate key. Third normal form removes transitive dependencies in which a non-key attribute depends on another non-key attribute.

Normalisation reduces insertion, update and deletion anomalies by representing facts in appropriate relations. Designers identify candidate keys and functional dependencies, then decompose relations while preserving information and useful constraints. Normalisation is not a command to create the maximum number of tables. The final model must also support real transactions, reporting and performance requirements.

User interface and interaction design

Interface design concerns navigation, layout, language, feedback, forms, errors, help and interaction behaviour. Begin with user tasks and context rather than decoration. Personas summarise relevant goals and constraints; task flows describe steps; wireframes explore structure; interactive prototypes test behaviour; and usability sessions reveal misunderstandings that designers may not anticipate.

A good interface makes the next action understandable, prevents avoidable mistakes and gives users confidence about what has happened. Controls should match the task, terminology should reflect users' language and feedback should be timely. Error messages should identify the issue and suggest a safe correction without exposing technical secrets. Consistency reduces learning effort, but screens should not be forced into identical patterns when tasks differ.

Accessibility, inclusion and responsive design

Accessibility should be built into design. Systems should support keyboard navigation, visible focus, meaningful headings, labels, sufficient contrast, text resizing, screen-reader interpretation and alternatives for non-text content. Colour must not be the only signal. Forms should associate instructions and errors with fields, and dynamic updates should be announced appropriately.

Responsive design adapts layout and interaction to different screen sizes and input methods. Flexible grids, relative units, appropriately sized controls and content prioritisation help services work on phones, tablets and desktops. Inclusion also considers language, literacy, bandwidth, device age and working conditions. Plain language, save-and-resume, low-bandwidth alternatives and user testing can reduce barriers that automated accessibility checks will not identify.

API design and integration

An API defines how one component requests a capability or exchanges data with another. A good contract specifies operations, resource names, request and response formats, validation, authentication, authorisation, error conventions, versioning and service expectations. It should expose business capabilities without leaking unnecessary internal details.

REST-style APIs commonly use HTTP methods: GET retrieves, POST creates or initiates processing, PUT replaces a representation, PATCH applies partial changes and DELETE requests removal. Idempotency matters when clients retry requests. Payment or order creation should use idempotency keys or deduplication controls where appropriate. Integration design also addresses timeouts, retries, rate limits, schema evolution, monitoring, ownership and change notification.

Security architecture and privacy by design

Security architecture identifies assets, actors, trust boundaries, threats and business impacts. Layered controls include identity verification, least-privilege authorisation, secure configuration, encryption, input validation, logging, monitoring, patching and tested recovery. Authentication establishes who is making a request; authorisation determines which resources and actions that identity may use.

Role-based access assigns permissions to roles; attribute-based access evaluates context such as department, location, resource classification or transaction value. Privacy by design limits collection to a defined purpose, restricts access, sets retention and deletion rules and supports applicable individual rights. Sensitive data should be classified. Threat modelling and privacy impact assessment should occur before deployment, not only after an incident.

Threat modelling and secure patterns

Threat modelling asks how a system could be attacked or misused. The team identifies assets, entry points, data flows, trust boundaries and likely adversaries, then considers threats and mitigations. STRIDE classifies spoofing, tampering, repudiation, information disclosure, denial of service and elevation of privilege. The model should be revisited when architecture or exposure changes.

Secure design patterns include deny-by-default, least privilege, complete mediation, secure failure, separation of duties and defence in depth. Validate input type, range, length and format; encode output for its context; and use parameterised queries to reduce injection risks. Logs should support investigation without unnecessarily recording passwords or tokens. Secrets require controlled storage and rotation, while dependency inventories support timely patching.

Cloud infrastructure and deployment

Infrastructure design selects compute, storage, network, identity and supporting services. On-premises infrastructure offers direct control but requires facilities, capital and operational capacity. Cloud services offer elastic resources and managed capabilities but introduce provider dependencies, usage-based costs, shared-responsibility obligations and configuration risks. IaaS supplies fundamental resources, PaaS manages more of the runtime and SaaS delivers a complete application.

Public, private, hybrid and multi-cloud arrangements suit different constraints. Selection should consider security, compliance, latency, skills, resilience, cost and integration. Deployment design defines environments, configuration, secrets, network exposure, scaling, backups, monitoring and rollback. Development, test, staging and production should be separated appropriately. Infrastructure as code and automated pipelines make deployments more repeatable, but do not remove the need for operational ownership.

Availability, resilience and disaster recovery

Availability is the proportion of agreed service time during which a system is usable. A target of 99.9 percent allows 0.1 percent unavailability over the measurement period. Reliability, recoverability and resilience are related but distinct. Redundant instances, health checks, load balancing, queues, circuit breakers, timeouts and graceful degradation can prevent a local fault from becoming a complete outage.

Recovery Time Objective is the maximum targeted time to restore a service after disruption. Recovery Point Objective is the maximum targeted data loss measured in time. Backups, replication and disaster recovery procedures must match these objectives and be tested. Redundancy is useful only when failure modes are sufficiently independent. An untested backup is an assumption, not proof of recoverability.

Performance, scalability and capacity

Performance includes response time, throughput and resource use. Profiling should distinguish browser rendering, network latency, application processing, database queries and external dependencies. Vertical scaling increases resources on one machine; horizontal scaling adds instances or nodes. Horizontal scaling may improve capacity and resilience but requires coordination, stateless application design or carefully managed shared state.

Caching reduces repeated computation and database load but requires decisions about freshness, invalidation and privacy. Capacity planning considers peak periods, bursts, growth, background jobs and failure scenarios rather than average load alone. Load, stress, soak and capacity tests establish operating limits. Systems should communicate overload clearly instead of silently losing transactions.

UML and systems modelling

UML provides standard diagram types for describing different aspects of a system. A use-case diagram shows actors and goals; a class diagram describes classes, attributes, operations and relationships; a sequence diagram shows messages over time; and an activity diagram represents workflow and decisions. A state-machine diagram describes states and transitions triggered by events or conditions.

Component diagrams show software modules and interfaces; deployment diagrams map artefacts to runtime nodes. UML diagrams should answer a defined question and remain consistent with requirements and other models. A diagram that attempts to show every detail becomes unreadable. Each model should state its name, scope and notation key where needed. Models are communication tools, not substitutes for stakeholder agreement.

Workflow and process design

Workflow design describes how work moves between people, software components and organisational units. It specifies triggers, activities, decisions, data, outputs, exceptions and completion conditions. Workflow engines can route tasks, enforce sequence, notify participants and record status, but the workflow must reflect real policy and operational needs.

Good workflow design minimises unnecessary handoffs and makes responsibility visible. It defines what happens when information is missing, approval is delayed, a service is unavailable or a request is rejected. Automation should not merely accelerate a defective process. Remove redundant steps, clarify decision rights and resolve conflicting data definitions first. Human review remains appropriate for ambiguous or high-impact decisions.

Analytics and decision-support design

Reporting design begins with decisions users need to make. Each measure requires a definition, source, owner, calculation, update frequency and permitted interpretation. Dashboards should distinguish actuals from targets, show the period and population represented and avoid misleading comparisons. Operational reports support daily control; management reports support resource decisions; analytical models explore patterns.

Warehouses and analytical pipelines can separate reporting workloads from transactional operations. Data lineage and quality checks help users understand whether a metric is complete and current. Decision-support systems combine data, models and scenario analysis. Forecasts are not facts, correlation is not causation and a precise-looking score can conceal uncertainty. Consequential outputs need explanation, validation and routes for challenge.

Design reviews, verification and validation

Reviews examine completeness, consistency, feasibility, security, accessibility, performance, maintainability and operational readiness. Prototyping and iterative design

A prototype is an early representation used to explore ideas, test assumptions or obtain feedback. Low-fidelity sketches are inexpensive for navigation and task structure. High-fidelity prototypes resemble the final interface and test details, but stakeholders may mistake them for completed products. Throwaway prototypes are discarded after learning; evolutionary prototypes are progressively refined toward delivery.

Iteration does not remove the need for architecture or governance. Feedback should be recorded, prioritised and linked to requirements. A prototype that receives positive comments from a few participants does not prove security, accessibility, scalability or suitability for all users. State the prototype's purpose, evaluation criteria and decision about what happens to its code and design after testing.

Decision analysis and trade-offs

Design decisions involve competing options. A weighted decision matrix compares alternatives against criteria such as cost, security, performance, usability, scalability, maintainability and delivery risk. Assign weights to reflect importance, score each option using evidence and calculate weighted totals. Mandatory legal or security requirements should not be traded away for a high aggregate score.

Sensitivity analysis tests whether the preferred option changes when weights or assumptions change. If a small adjustment reverses the ranking, the decision is fragile and needs more evidence. A decision record explains constraints, uncertainty, rejected alternatives and conditions that would trigger reconsideration. The matrix structures discussion; it does not eliminate professional judgement.

Legacy integration and migration

Legacy systems may contain valuable data and business rules even when technology is outdated. Strategies include wrapping an existing system with APIs, synchronising data, replacing modules incrementally or migrating to a new platform. Selection depends on continuity, data quality, interface availability, vendor support and the cost of parallel operation.

Migration planning covers profiling, cleansing, mapping, transformation, validation, reconciliation, cutover and rollback. Count records, sample content, reconcile totals and relationships, document exceptions and obtain business approval. Big-bang cutover concentrates risk; phased migration reduces each change but creates coexistence and synchronisation complexity. A successful database load does not prove that business meaning has been preserved.

Ethical and professional responsibilities

Systems influence access to education, employment, finance, health and public services. Design choices about eligibility, defaults, data collection and automated decisions may create unequal effects. Worked data-model example

An applicant may submit several applications, but each application belongs to exactly one applicant. This is a one-to-many relationship. ApplicantID is the primary key of Applicant and a foreign key in Application; ApplicationID uniquely identifies each application. A unique constraint may prevent duplicate applications for the same applicant, programme and admission cycle if policy requires it.

A spreadsheet with Programme1, Programme2 and Programme3 columns creates a repeating group and limits choices. A normalised model stores one applicant row and a separate application row for each choice. A transaction should create the application and its audit event consistently. The precise uniqueness rule must be confirmed with admissions policy rather than invented by the database designer.

Worked availability calculation

A portal is required to achieve 99.5 percent monthly availability. A 30-day month contains 30 × 24 × 60 = 43,200 minutes. The unavailable time permitted by a 0.5 percent allowance is 43,200 × 0.005 = 216 minutes, or 3 hours 36 minutes. This is meaningful only when the measurement window and exclusions are defined.

If the business sets an RTO of two hours and an RPO of fifteen minutes, recovery must restore an operational service within two hours and limit data loss to no more than fifteen minutes of accepted transactions. A recovery exercise should restore to an isolated environment, validate integrity, measure elapsed time and record gaps. If restoration takes three hours, the RTO has not been met even if backup files exist.

Applied design workshop 1: Purpose of systems design

Consider a public-facing university information service used by applicants, students, lecturers, administrators and external partners. The design team must identify the primary task, the data required, the authority permitted to perform each action and the failure conditions that could interrupt the service. For this workshop, apply the topic of purpose of systems design to the service and prepare a concise design artefact that can be reviewed by a mixed technical and business team.

Systems design translates approved requirements into a coherent description of how people, processes, data, software, infrastructure and controls will work together. Analysis establishes the problem and required outcomes; design specifies the solution structure and its behaviour. It is not merely screen drawing or database creation. It is a set of models, decisions and specifications that guide implementation, testing, deployment and maintenance.

A sound design balances usability, security, performance, availability, cost, accessibility and maintainability. Stakeholders may have conflicting priorities, so trade-offs and assumptions must be explicit. A design should be evaluated against measurable requirements and the real context of use. A technically elegant product that fails to support the work is unsuccessful, just as a convenient interface that exposes confidential information is unsuccessful.

Evaluate the proposal against usability, accessibility, security, performance, maintainability and cost. Identify at least two alternatives and explain why the selected option is preferable in the stated context. State one measurable acceptance criterion, one operational risk, one mitigation and one item that requires stakeholder approval. Applied design workshop 9: Relational design and normalisation

Consider a public-facing university information service used by applicants, students, lecturers, administrators and external partners. For this workshop, apply the topic of relational design and normalisation to the service and prepare a concise design artefact that can be reviewed by a mixed technical and business team.

First normal form removes repeating groups and requires fields to hold atomic values appropriate to their domain. Storing several telephone numbers in one comma-separated field makes validation and querying difficult. Second normal form removes partial dependencies on part of a composite candidate key. Third normal form removes transitive dependencies in which a non-key attribute depends on another non-key attribute.

Normalisation reduces insertion, update and deletion anomalies by representing facts in appropriate relations. Designers identify candidate keys and functional dependencies, then decompose relations while preserving information and useful constraints. Normalisation is not a command to create the maximum number of tables. The final model must also support real transactions, reporting and performance requirements.

Architecture and design diagrams

University examination and revision questions

Use diagrams and justified examples where appropriate. The model answers state core marking points; formal answers should develop the reasoning and state relevant assumptions.

Question 1. Differentiate systems analysis from systems design.

Model answer: Analysis establishes the problem, stakeholder needs and outcomes; design specifies the structure and mechanisms through which the solution meets them. Analysis focuses on what and why, design on how.

Question 2. Explain high cohesion and low coupling.

Model answer: High cohesion keeps a module focused on a related purpose. Low coupling limits dependence on other modules' internal details. Both improve testing, comprehension and safe change.

Question 3. Name six quality attributes.

Model answer: Examples are performance, availability, reliability, scalability, security, usability, accessibility and maintainability. Define each in measurable terms appropriate to the service.

Question 4. Compare layered and microservices architectures.

Model answer: Layered design separates responsibilities within an application and is often simpler to operate. Microservices permit independent deployment and scaling but add network, monitoring and distributed-data complexity.

Question 5. What is an architectural decision record?

Model answer: A record of context, alternatives, decision, consequences and status. It preserves reasoning and supports future review.

Question 6. Differentiate conceptual, logical and physical data models.

Model answer: Conceptual models show business entities and relationships; logical models add attributes, keys and constraints; physical models specify database tables, types, indexes and storage.

Question 7. Explain database normalisation.

Model answer: It organises relations to reduce redundancy and insertion, update and deletion anomalies using keys and functional dependencies.

Question 8. State first, second and third normal forms.

Model answer: 1NF removes repeating groups; 2NF removes partial dependencies on a composite key; 3NF removes transitive dependencies of non-key attributes.

Question 9. Why is client-side validation insufficient?

Model answer: Users can alter browser code or send requests directly. The server must independently validate data and enforce permissions and business rules.

Question 10. Give four accessible interface requirements.

Model answer: Keyboard operation and visible focus; semantic labels and headings; adequate contrast; screen-reader support; zoom and clear error instructions.

Question 11. What belongs in an API contract?

Model answer: Operations, request and response schemas, authentication, authorisation, validation, errors, versioning and service expectations.

Question 12. Differentiate authentication and authorisation.

Model answer: Authentication verifies identity; authorisation determines what that identity may access or do.

Question 13. Explain defence in depth.

Model answer: Multiple complementary controls reduce the chance that one failure exposes the entire system, for example identity controls, least privilege, encryption, monitoring and recovery.

Question 14. Define RTO and RPO.

Model answer: RTO is the target maximum service restoration time. RPO is the target maximum data loss measured in time.

Question 15. Calculate downtime for 99.9% availability over 30 days.

Model answer: 30 days = 43,200 minutes. Allowed downtime = 0.001 × 43,200 = 43.2 minutes.

Question 16. Compare vertical and horizontal scaling.

Model answer: Vertical scaling adds resources to one node; horizontal scaling adds nodes. Horizontal scaling requires coordination and management of shared state.

Question 17. What do UML use-case and sequence diagrams show?

Model answer: Use-case diagrams show actors and goals; sequence diagrams show time-ordered messages between participants.

Question 18. Why are workflow exception paths important?

Model answer: They define safe handling, responsibility and escalation for missing data, rejection, delay and service failure.

Question 19. Differentiate verification and validation.

Model answer: Verification checks conformance to specifications; validation checks whether the solution addresses the real user and business need.

Question 20. Compare throwaway and evolutionary prototypes.

Model answer: Throwaway prototypes are discarded after learning; evolutionary prototypes are progressively refined toward delivery and require stronger engineering controls.

Question 21. How does a weighted decision matrix help?

Model answer: It weights criteria, scores options and calculates totals to structure comparison, while leaving mandatory constraints and judgement explicit.

Question 22. Identify four data migration risks.

Model answer: Poor source quality, incorrect mapping, lost relationships, duplicates, downtime, incomplete reconciliation and failed rollback.

Question 23. What is threat modelling?

Model answer: A structured analysis of assets, entry points, trust boundaries, threats and mitigations during design.

Question 24. A service completes 720 requests in 12 minutes. Find throughput.

Model answer: 720 ÷ 12 = 60 completed requests per minute.

Question 25. A service has a 2-hour RTO and 15-minute RPO. What must be tested?

Model answer: Restore an operational service within two hours and demonstrate that no more than fifteen minutes of accepted data is lost.

Question 26. Explain privacy by design.

Model answer: Embed purpose limitation, data minimisation, access control, security, retention, deletion, transparency and applicable user rights into the solution from the outset.

Question 27. Why not adopt microservices solely because they are popular?

Model answer: They introduce distributed communication, security, operational and consistency complexity. Use them only when independent ownership, deployment or scaling justifies the cost.

Question 28. Why is requirements traceability important?

Model answer: It links requirements to design elements and tests, supporting completeness, impact analysis, verification and controlled change.

Question 29. Describe a phased university data migration.

Model answer: Profile and cleanse; map and test transformations; pilot a faculty; reconcile and obtain approval; migrate in waves; monitor; retain rollback and continuity plans.

Question 30. State three ethical responsibilities of designers.

Model answer: Protect privacy and security; assess unequal impacts and accessibility; explain limitations; enable challenge of consequential decisions; report risks honestly.
